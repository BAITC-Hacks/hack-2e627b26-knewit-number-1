## 1. Назначение документа

Настоящее техническое задание определяет цели, границы, функциональные и нефункциональные требования, интеграции, правила безопасности, критерии приёмки и состав результатов разработки ИИ-ассистента для сайта [ekt.kz](https://ekt.kz/).

Ассистент должен консультировать клиентов по каталогу электротехнической продукции, сообщать актуальные цену и наличие, предоставлять характеристики и доступные документы, помогать подобрать аналог и, только после явного подтверждения пользователя, добавлять выбранный товар в корзину.

Документ является основанием для проектирования, разработки, тестирования и демонстрации решения. Неопределённые интеграционные параметры перечислены в разделе 19 и должны быть согласованы с владельцем продукта до промышленного запуска.

## 3. Исходная проблема

Клиенты ekt.kz вынуждены обращаться к менеджеру, чтобы:

- найти товар по названию, артикулу или характеристикам;
- уточнить технические характеристики и наличие на складах;
- получить сертификат или иную сопроводительную документацию;
- подобрать замену отсутствующей позиции;
- узнать условия оплаты, доставки и минимальной партии;
- добавить подобранную позицию в корзину.

Это увеличивает время принятия решения, создаёт нагрузку на менеджеров и повышает вероятность ухода клиента до оформления заказа.

## 4. Цели и показатели успеха

### 4.1. Цели

1. Сократить время от вопроса клиента до получения релевантного ответа.
2. Автоматизировать типовые консультации без снижения достоверности данных.
3. Увеличить долю пользователей, переходящих из консультации в корзину.
4. Снизить нагрузку на менеджеров по повторяющимся вопросам.
5. Обеспечить безопасное изменение корзины только по подтверждённой команде пользователя.

### 4.2. Целевые метрики

Значения для промышленного запуска уточняются после базового замера. Для MVP применяются следующие ориентиры:

| Метрика | Целевое значение MVP |
|---|---:|
| Корректность ответа по известному артикулу на контрольной выборке | не менее 95% |
| Ответы с выдуманными ценами или остатками | 0 |
| Добавления в корзину без явного подтверждения | 0 |
| Доля успешных поисков существующего товара из тестовой выборки | не менее 90% |
| p95 времени текстового ответа без обработки вложения | не более 5 секунд при доступности зависимостей |
| p95 проверки цены и наличия одного товара | не более 3 секунд при доступности API ekt.kz |

Бизнес-метрики для пилота: конверсия «чат → корзина», доля вопросов без участия менеджера, среднее время консультации, доля эскалаций и оценка ответа пользователем.

Метрики качества рассчитываются на версионируемой размеченной выборке не менее чем из 200 запросов: точный артикул/ID — не менее 20%, название и опечатки — не менее 25%, поиск по характеристикам — не менее 30%, отсутствие и аналоги — не менее 25%. Запрос считается корректно обработанным, если найден эталонный товар в допустимом top-k, не искажены обязательные поля и соблюдено ожидаемое действие. Формулы: `accuracy = корректные ответы / все применимые запросы`, `search success = запросы с эталоном в top-k / запросы, для которых эталон существует`. Версия каталога, правил и модели фиксируется в отчёте; изменения эталона проходят экспертное согласование.

### 4.3. Стратегия конкурентного MVP для хакатона

Цель команды — не только формально закрыть must-have, но и гарантировать воспроизводимую демонстрацию независимо от момента выдачи данных партнёром.

| Приоритет | Результат | Критерий готовности к демо |
|---|---|---|
| Critical path | Доступ к реальному API ekt.kz | Запрос организаторам отправлен немедленно; проверены credentials, минимум две страницы списка, detail для доступного и отсутствующего товара |
| Critical fallback | Синтетический каталог с реальной структурой полей | Прототип полностью работает через переключаемый mock provider; режим синтетических данных явно обозначен |
| Must-have | Статичная версия базы условий покупки | Ответы об оплате, доставке и самовывозе имеют официальный URL, дату проверки и статус согласования |
| Must-have | Объяснимый аналог | В карточке показаны совпадения, отличия и причина рекомендации, а не только список товаров |
| Must-have | Безопасное подтверждение корзины | Нестандартные и неоднозначные фразы не создают побочных эффектов |
| Winning feature | Казахский язык | Ключевой сквозной сценарий поиска и консультации демонстрируется на казахском языке |

Синтетические данные являются резервом для разработки и демонстрации, но не выдаются за live-данные партнёра. На экране и в логах должен отображаться активный источник: `LIVE EKT API` либо `DEMO FIXTURE`.

### 5.1. Входит в MVP (P0)

- чат-виджет на десктопной и мобильной версиях сайта;
- диалог на русском языке;
- поиск товара по идентификатору, артикулу, названию и текстовому описанию потребности;
- получение актуальной детальной информации о товаре через API;
- показ цены, доступного остатка, основных характеристик, изображения и ссылки на карточку товара;
- ответы по условиям покупки из согласованной базы знаний;
- подбор аналогов при отсутствии товара или по прямому запросу;
- безопасный сценарий подтверждения и добавления товара в корзину;
- предоставление ссылки на актуальную корзину;
- обработка ошибок и возможность предложить обращение к менеджеру;
- журналирование технических событий и продуктовых метрик без записи секретов и избыточных персональных данных.

### 5.2. Следующий приоритет (P1)

- поддержка казахского языка, включая отдельный демонстрационный сценарий (главный winning feature);
- обработка вложений PDF, DOCX, XLSX, JPEG и PNG;
- распознавание товарных позиций в спецификациях, накладных и фотографиях;
- подбор сопутствующих товаров;
- история диалогов для авторизованных пользователей;
- передача диалога менеджеру с кратким резюме;

### 5.3. Не входит в MVP

- самостоятельное оформление или оплата заказа;
- сбор и хранение данных банковских карт;
- изменение цен, складских остатков и карточек товаров;
- предоставление юридически значимых гарантий совместимости без подтверждённых данных;
- голосовой интерфейс;
- обучение базовой LLM на персональных данных клиентов;
- замена CRM, ERP, учётной системы или штатной корзины сайта.

## 7. Основные пользовательские сценарии

### 7.1. Поиск конкретного товара

1. Пользователь вводит артикул, идентификатор или название.
2. Ассистент выполняет поиск по локальному индексу каталога.
3. Для выбранного товара ассистент запрашивает детальные данные через API.
4. Ассистент показывает название, артикул, цену, статус наличия, основные характеристики и ссылку на карточку товара.
5. Если найдено несколько вариантов, ассистент показывает краткий список и просит выбрать нужный.

### 7.2. Поиск по характеристикам

1. Пользователь описывает назначение или параметры товара свободным текстом.
2. Ассистент выделяет обязательные и желательные параметры.
3. При недостатке данных задаёт не более одного-двух уточняющих вопросов за итерацию.
4. Ассистент показывает до пяти подходящих позиций и объясняет соответствие запросу.

### 7.3. Товар отсутствует

1. Ассистент получает нулевой доступный остаток.
2. Не предлагает добавить отсутствующий товар в корзину.
3. Ищет аналоги по категории, назначению и ключевым параметрам.
4. Показывает отличия каждого аналога от исходной позиции.
5. Если надёжного аналога нет, честно сообщает об этом и предлагает обратиться к менеджеру.

### 7.4. Добавление в корзину

1. Пользователь выбирает товар и количество.
2. Ассистент повторно запрашивает актуальные цену и остаток.
3. Ассистент выводит резюме: товар, артикул, количество, цена за единицу и сумма — и спрашивает подтверждение.
4. Только после однозначного подтверждения вызывает API корзины.
5. Ассистент сообщает результат и возвращает прямую ссылку на корзину.
6. При изменении цены или остатка подтверждение считается устаревшим; ассистент сообщает новые данные и запрашивает подтверждение повторно.

### 7.5. Вопрос об условиях покупки

1. Пользователь спрашивает об оплате, доставке, самовывозе, минимальной партии, возврате или графике работы.
2. Ассистент отвечает только по согласованной базе знаний.
3. В ответе указывается релевантное условие и, если возможно, ссылка на официальный раздел сайта.
4. Если информации нет или она неоднозначна, вопрос передаётся менеджеру либо показывается официальный канал связи.

### 7.6. Обработка файла (P1)

1. Пользователь прикладывает спецификацию, накладную или фотографию.
2. Система проверяет тип и размер файла, выполняет антивирусную проверку и извлекает текст/OCR.
3. Ассистент формирует распознанный перечень позиций и просит подтвердить его.
4. По каждой подтверждённой строке выполняется поиск товара или аналога.
5. Массовое добавление также требует финального явного подтверждения состава и количества.

## 8. Источники данных и API ekt.kz

### 8.1. Общие требования к интеграции

- Базовый адрес: `https://ekt.kz/api`.
- Формат ответа: JSON в кодировке UTF-8.
- При запросе без учётных данных на 23.09.2026 сервер возвращает `HTTP 401 Unauthorized` и объявляет схему `WWW-Authenticate: Basic realm="IJUK API"`. Это подтверждает Basic challenge, но не подтверждает успешную авторизацию, состав прав и стабильность контракта; они должны быть проверены с выданными владельцем API учётными данными.
- Учётные данные должны храниться только в менеджере секретов или переменных окружения серверной части.
- Запрещено передавать логин или пароль API в браузер, мобильный клиент, LLM-промпт, клиентские журналы или репозиторий.
- Все обращения выполняются только по HTTPS из серверного интеграционного слоя.
- Точные лимиты запросов, SLA и правила использования API предоставляет владелец ekt.kz.

### 8.2. Список товаров

**Метод и URL:** `GET https://ekt.kz/api/products`

**Назначение:** получение первой страницы списка товаров.

**Параметры запроса:** подтверждено использование `page` для перехода к указанной странице. Остальные параметры, индекс первой страницы и поведение при отсутствии `page` требуют проверки на авторизованном ответе.

**Формат предоставленного примера элемента списка:**

| Поле | Тип по примеру | Наблюдалось в примере | Назначение |
|---|---|---:|---|
| `id` | integer | да | Уникальный идентификатор товара |
| `name` | string | да | Наименование товара |
| `article` | string | да | Артикул; сравнение должно поддерживать кириллицу и регистронезависимый режим |
| `price` | number | да | Текущая цена; валюта должна быть подтверждена владельцем API |
| `image` | string (URL) | да | URL изображения |
| `url` | string (URL) | да | URL публичной карточки товара |
| `url_api_detail` | string (URL) | да | URL детального API-ответа |
| `offers` | array | да | Торговые предложения/вариации; структура элемента требует отдельного примера |

Колонка «Наблюдалось в примере» не задаёт обязательность поля. До получения JSON Schema/OpenAPI парсер должен корректно обрабатывать отсутствие и `null`, а минимально необходимые для функции поля должны проверяться прикладной валидацией.

Пример элемента:

```json
{
  "id": 45357,
  "name": "***LED STARK 30W 2400Lm d98x180 4000K IP20 MEGALIGHT (20)",
  "article": "ярп4520",
  "price": 1810,
  "image": "https://ekt.kz/upload/iblock/.../led_stark_30w_2400lm_d98x180_4000k_ip20_megalight_20.jpg",
  "url": "https://ekt.kz/catalog/.../",
  "url_api_detail": "https://ekt.kz/api/products/detail?id=45357",
  "offers": []
}
```

### 8.3. Пагинация списка

**Метод и URL:** `GET https://ekt.kz/api/products?page={page}`

Пример второй страницы: `GET https://ekt.kz/api/products?page=2`.

Требования:

- `page` передаётся как положительное целое число, начиная с согласованной первой страницы;
- загрузчик не должен заранее предполагать размер страницы;
- условие окончания обхода должно быть подтверждено на реальном ответе API: пустой массив, метаданные пагинации либо иной признак;
- повторная загрузка одной страницы не должна создавать дубликаты; ключ данных — `id`;
- загрузчик должен защищаться от бесконечного обхода: максимальное число страниц задаётся конфигурацией и сопровождается предупреждением мониторинга;
- порядок элементов API не считается постоянным;
- до получения документированной схемы пагинации запрещено делать предположение о наличии полей `total`, `next` или `page_count`.

### 8.4. Детальная информация о товаре

**Метод и URL:** `GET https://ekt.kz/api/products/detail?id={id}`

Пример: `GET https://ekt.kz/api/products/detail?id=515291`.

| Поле | Тип по примеру | Наблюдалось в примере | Назначение / правило обработки |
|---|---|---:|---|
| `id` | integer | да | Уникальный идентификатор товара |
| `name` | string | да | Наименование |
| `article` | string | да | Артикул |
| `description` | string | да | Неструктурированное описание и характеристики |
| `price` | number | да | Актуальная цена |
| `quantity` | number | да | Общий остаток по версии API; бизнес-смысл требует подтверждения |
| `stores` | array | да | Остатки в разрезе складов/типов хранения |
| `stores[].id` | integer | да | Идентификатор склада |
| `stores[].name` | string | да | Название склада |
| `stores[].quantity` | number | да | Остаток на складе |
| `image` | string (URL) | да | Основное изображение |
| `url` | string (URL) | да | Публичная карточка товара |
| `offers` | array | да | Варианты/торговые предложения; схема требует подтверждения |
| `properties` | object | да | Расширяемый словарь свойств товара |

Подтверждённые примеры ключей `properties`: `BRAND_PRIORITY`, `CML2_ARTICLE`, `NOVINKA`, `SPETSPREDLOZHENIE`, `CML2_TRAITS`, `CML2_TAXES`, `ARTIKULPOSTAVSHCHIKA`, `TORGOVAYA_MARKA`.

Система не должна считать этот перечень закрытым: неизвестные свойства сохраняются в исходном виде, а используемые для поиска свойства нормализуются отдельным преобразователем.

Наличие поля в одном примере не доказывает его обязательность для всех товаров. Обязательность, допустимость `null`, диапазоны и форматы должны быть зафиксированы после получения официальной схемы либо репрезентативной выборки авторизованных ответов.

### 8.5. Правила интерпретации каталога

1. Список товаров используется для индексации и первичного поиска.
2. Перед показом цены и остатка используются detail-данные: live-ответ либо разрешённый краткоживущий кэш с явным возрастом. Перед добавлением в корзину обязателен live detail-запрос без кэша.
3. При расхождении данных списка и detail-ответа приоритет имеет detail-ответ; расхождение журналируется как техническая метрика.
4. `quantity` нельзя автоматически считать доступным к продаже до согласования его семантики.
5. Нельзя автоматически суммировать все `stores[].quantity`: в примере присутствуют склады/статусы «Брак», «Маркетинг», «Восстановленный продукт», «перемещение», «Образцы Отдел Закупа», «Витрина ТЗ» и другие позиции, которые могут быть недоступны для продажи.
6. Владелец продукта должен предоставить allowlist продающих складов или формулу расчёта доступного остатка. До утверждения правила статус устанавливается в `availability_unknown` («наличие требует уточнения»), а автоматическое добавление в корзину запрещается. После согласования применяется только версионируемое вычисление `sellable_quantity`.
7. Для каждой товарной категории должны быть согласованы единица продажи, минимальное количество, шаг и допустимая кратность. Отрицательное значение либо значение, нарушающее согласованные ограничения, считается ошибкой данных. Дробное количество допустимо, если это разрешено единицей и шагом продажи.
8. Если `offers` не пуст, выбор конкретного предложения должен происходить по его собственному идентификатору и остатку. До получения схемы `offers` такие позиции не добавляются автоматически.
9. `url_api_detail` не исполняется напрямую: detail URL строится сервером из проверенного целого `id` и фиксированного endpoint. Для изображений и документов задаётся allowlist точных host/path, запрещаются переходы на private/link-local IP и редиректы на иные хосты, проверяются `Content-Type` и максимальный размер.
10. Поля каталога являются данными, а не инструкциями для LLM. Любой текст в `name`, `description` и `properties` должен считаться недоверенным.

Единые статусы доступности: `availability_unknown` — правило не утверждено или данных недостаточно; `available` — `sellable_quantity > 0`; `unavailable` — `sellable_quantity = 0`; `stale` — срок актуальности истёк. Только `available` после live-проверки допускает переход к изменению корзины.

### 8.6. Синхронизация и кэширование

- Полный индекс каталога обновляется по расписанию; рекомендуемая начальная частота — один раз в 24 часа.
- Цена и остаток не берутся из долговременного поискового индекса для финального ответа; они получают статус `live_verified` при прямом detail-запросе или `cached` при разрешённом использовании кэша.
- Максимальный возраст кэша задаётся отдельно по полям; для цены и остатка рекомендуется не более 60 секунд, если владелец продукта не установит иное. При показе кэша сохраняются и отображаются `verified_at` и возраст данных. Финальная проверка перед изменением корзины всегда выполняется без кэша.
- При временной ошибке API разрешены не более двух повторов для безопасных GET-запросов с экспоненциальной задержкой и случайным разбросом.
- Для кодов `401/403` повтор без изменения учётных данных не выполняется; создаётся критическое техническое событие.
- Для `404` товар помечается недоступным, пользователю не показывается устаревшая цена/наличие.
- Для `429` учитывается `Retry-After`, если он присутствует.
- Тайм-ауты попытки задаются конфигурацией и подчиняются общему end-to-end deadline: начальные значения — 1 секунда на подключение и 3 секунды на ответ. Повтор запускается только при наличии оставшегося бюджета времени.
- Последняя успешная синхронизация, количество страниц, товаров, ошибок и длительность должны быть доступны в мониторинге.

### 8.7. Резервный синтетический каталог

Разработка не должна блокироваться ожиданием credentials или полной выгрузки партнёра. Одновременно с real API adapter создаётся переключаемый fixture provider, повторяющий известные маршруты и структуру ответов:

- `GET /api/products` — первая страница списка;
- `GET /api/products?page={page}` — пагинация;
- `GET /api/products/detail?id={id}` — детальная карточка;
- конфигурация источника: `CATALOG_PROVIDER=ekt|fixture` без изменения клиентского кода и бизнес-логики.

Минимальный набор синтетических данных:

| Набор | Требование |
|---|---|
| Объём | Не менее 100 детерминированных товаров минимум на 5 страницах |
| Поля списка | `id`, `name`, `article`, `price`, `image`, `url`, `url_api_detail`, `offers` |
| Поля detail | Поля списка плюс `description`, `quantity`, `stores`, `properties` |
| Наличие | Доступные, отсутствующие и `availability_unknown` позиции; доступность считается тем же правилом, что и в live-режиме |
| Поиск | Точные артикулы, кириллица, похожие названия, опечатки и несколько кандидатов на запрос |
| Аналоги | Минимум 10 экспертно связанных групп с совпадающими и отличающимися критичными характеристиками |
| Склады | Продающие и непродающие склады, включая «Брак» и «перемещение», для проверки allowlist |
| Ошибки | Fixtures для `401`, `404`, `429`, `5xx`, тайм-аута, отсутствующего поля и `null` |

Правила подготовки:

1. Идентификаторы не пересекаются случайно, seed генерации и версия набора фиксируются.
2. `offers` присутствует как массив. Пока официальная структура непустого элемента не получена, используется только `offers: []`; выдуманный контракт вариаций запрещён.
3. Изображения и ссылки используют локальные безопасные fixtures либо явно маркированные публичные ссылки.
4. Mock должен повторять пагинацию, коды ошибок и задержки, чтобы интеграционные тесты не зависели от реального API.
5. Все демонстрационные ответы содержат признак `data_source=fixture`; скриншоты и презентация не должны представлять их как реальные остатки или цены ekt.kz.
6. После получения доступа один и тот же набор контрактных тестов запускается для fixture и live provider; различия документируются.

Критерий аварийной готовности: если live-доступ отсутствует к началу интеграционного этапа, команда продолжает разработку и репетицию на fixture provider, а подключение реального источника ограничивается заменой адаптера и повторным прогоном контрактных тестов.

Сообщение, меняющее товар, предложение или количество, создаёт новое резюме и требует нового подтверждения. |
| FR-CART-005 | P0 | Сервер создаёт одноразовый `action_id`, привязанный к пользователю, диалогу, версии сообщения, корзине и её версии, товару/offer, точному количеству, цене, валюте, версии/контексту ценообразования и сроку действия не более 5 минут. Использованный, истёкший или чужой `action_id` отклоняется; новое резюме в диалоге погашает предыдущее. |
| FR-CART-006 | P0 | Непосредственно перед изменением корзины цена и `sellable_quantity` повторно проверяются live-запросом без кэша. |

| FR-CART-009 | P0 | Один `action_id` всегда использует один и тот же idempotency key. Повтор сообщения, ответа или сетевой retry не создаёт новый ключ и не дублирует позицию. |
| FR-CART-010 | P0 | После успеха ассистент показывает фактически добавленное количество и прямую ссылку на актуальную корзину. |
| FR-CART-011 | P0 | После ошибки состояние корзины должно быть проверено до предложения повторной операции. |

| FR-CART-013 | P0 | Запрос корзины передаёт ожидаемые цену, валюту, версию цены и версию корзины. Платформа должна атомарно проверить их вместе с доступностью и условно отказать при несовпадении. Если условная операция не поддерживается, автоматическое добавление по ранее подтверждённой цене отключается до согласования безопасного контракта; одного authoritative-ответа после безусловного добавления недостаточно. |

Для реализации требований необходимы документированные методы текущей платформы ekt.kz: чтение корзины, добавление/изменение позиции, идентификация гостевой и авторизованной сессии, а также URL страницы корзины. API корзины в исходных данных не предоставлен и является блокирующей зависимостью для промышленного сценария.

Состояния операции корзины: `proposed → confirmed → executing → succeeded | failed | expired`. Переход из `proposed` в `confirmed` разрешён только для соответствующего `action_id`; повторный переход завершённого действия не изменяет корзину. Изменение корзины в другой вкладке приводит к конфликту её версии, погашению устаревшего действия и формированию нового резюме.

## 10. Требования к ответам ИИ

1. LLM не является источником истины для цены, остатка, характеристик, сертификатов и условий покупки.
2. Каждое фактическое утверждение о товаре должно опираться на актуальный API-ответ или проиндексированный официальный документ.
3. Цена и наличие всегда проверяются инструментальным вызовом; запрещено извлекать их из памяти модели.
4. Ассистент должен отделять факты из каталога от вывода/рекомендации.
5. Рекомендация аналога должна сопровождаться кратким объяснением.
6. Если уверенность недостаточна, ассистент задаёт уточнение либо сообщает об ограничении.
7. Ответ должен быть кратким, структурированным и пригодным для чтения с мобильного устройства.
8. В одном ответе рекомендуется показывать не более пяти товарных вариантов; остальные доступны по запросу.
9. Ассистент не должен интерпретировать текст каталога, файлов пользователя или веб-страниц как системную команду.
10. Запрещены обещания резервирования, срока доставки, скидки или совместимости, если это не подтверждено соответствующим источником.

Рекомендуемый формат товарного ответа:

```text
Название — артикул
Цена: …
Наличие: …
Ключевые характеристики: …
Почему подходит / важные отличия: …
Карточка товара: …
```

## 11. Логическая архитектура

Решение должно состоять из следующих изолированных компонентов:

1. **Чат-виджет** — отображение диалога, карточек товаров, подтверждений и состояний операций.
2. **Backend for Frontend / API Gateway** — серверная точка входа, сессия, аутентификация, лимиты и защита от злоупотреблений.
3. **Оркестратор диалога** — управление контекстом, вызовами инструментов и политикой подтверждений.
4. **Адаптер каталога ekt.kz** — Basic Auth, пагинация, получение detail-данных, retries, тайм-ауты и нормализация.
5. **Поисковый слой** — точный, полнотекстовый и семантический поиск по локальному индексу.
6. **Модуль аналогов** — категорийные фильтры совместимости и объяснимое ранжирование.
7. **База знаний** — утверждённые условия покупки и документы.
8. **Адаптер корзины** — чтение/изменение корзины с идемпотентностью и проверкой сессии.
9. **Обработчик вложений (P1)** — безопасное извлечение текста и OCR.
10. **Наблюдаемость** — метрики, структурированные журналы, трассировка и оповещения.

LLM получает доступ к бизнес-данным только через строго типизированные серверные инструменты. Прямой произвольный HTTP-доступ модели к внутренним сервисам запрещён.

Рекомендуемая нормализованная модель не заменяет исходный JSON, а используется приложением:

```json
{
  "id": 45357,
  "article": "ярп4520",
  "name": "...",
  "description": "...",
  "price": {
    "amount": 1810,
    "currency": null,
    "verified_at": "ISO-8601"

    "sellable_quantity": null,
    "unit": null,
```

## 13. Нефункциональные требования

### 13.1. Производительность

- Отсчёт end-to-end latency начинается при приёме сообщения сервером и заканчивается передачей полного ответа клиенту; отдельно измеряется time-to-first-token для потокового ответа.
- Индикатор обработки должен появиться не позднее 300 мс, первый токен — не позднее 2 секунд, p95 полного ответа без вложений — не более 5 секунд при доступности зависимостей в пределах их SLO.
- Общий deadline текстового запроса — 8 секунд. Бюджеты внутренних вызовов и retries должны укладываться в него; при исчерпании deadline система завершает запрос контролируемым сообщением, а не продолжает фоновое изменение состояния.
- Длительная операция должна сообщать о прогрессе или разделяться на этапы.
- Поисковый индекс должен обеспечивать выдачу кандидатов не более чем за 1 секунду на целевом объёме каталога.
- Профиль приёмочного нагрузочного теста фиксируется после получения целевых значений одновременных чатов и сообщений в минуту; окружение, объём каталога и состояние внешних сервисов указываются в отчёте.

### 13.2. Надёжность

- Ошибка LLM или внешнего API не должна повреждать корзину или сессию.
- Каждое логическое действие корзины имеет уникальный `action_id` и стабильный idempotency key, повторно используемый во всех retries этого действия.
- Компоненты должны корректно обрабатывать `400`, `401`, `403`, `404`, `409`, `422`, `429` и `5xx`.
- Для промышленной эксплуатации целевая доступность серверной части — не менее 99,5% в месяц, без учёта согласованных окон обслуживания и недоступности внешних систем.
- Должны быть предусмотрены health/readiness probes и контролируемая деградация: при недоступности detail API нельзя показывать цену/наличие как актуальные.

### 13.3. Совместимость и адаптивность

- Последние две стабильные версии Chrome, Edge, Firefox и Safari.
- Адаптивная ширина от 320 px.
- Чат не должен перекрывать ключевые элементы навигации, cookie-баннер или кнопку оформления заказа.
- Ссылки должны открываться безопасно; для новой вкладки применяется `rel="noopener noreferrer"`.

### 13.4. Доступность

- Целевой уровень — WCAG 2.2 AA.
- Полная работа с клавиатуры, видимый фокус, корректные ARIA-атрибуты и сообщения screen reader.
- Контраст текста и элементов управления соответствует WCAG AA.
- Информация не передаётся только цветом.
- Для изображений товаров используется осмысленный `alt` либо пустой `alt` для декоративных изображений.

### 13.5. Локализация

- Все пользовательские строки должны храниться отдельно от кода.
- Базовая локаль — `ru-KZ`; дополнительная — `kk-KZ` (P1).
- Числа, валюта, дата и время форматируются по выбранной локали.
- Артикулы и названия не переводятся автоматически.

## 14. Информационная безопасность и приватность

1. Секреты API хранятся в защищённом хранилище и ротируются по регламенту.
2. Клиентский код не содержит секретов или внутренних адресов.
3. Сервер валидирует все параметры независимо от проверки в интерфейсе.
4. Для операций корзины применяется защита сессии, CSRF и проверка принадлежности корзины пользователю.
5. Ввод, каталог, загруженные файлы и найденные документы считаются недоверенными данными; должны действовать меры против prompt injection и подмены инструментальных вызовов.
6. Модель не получает возможность формировать произвольные вызовы корзины: параметры проходят проверку по JSON-схеме и бизнес-правилам.
7. HTML/Markdown в ответах санитизируется; выполнение скриптов и опасных URL запрещено.
8. Применяются ограничения частоты запросов по IP/сессии и защита от автоматизированного злоупотребления.
9. Журналы не должны содержать пароль API, cookie, токены, полные персональные данные или содержимое файлов сверх необходимого.
10. Срок хранения диалогов, вложений и технических журналов должен быть утверждён владельцем продукта. Пользователь информируется о хранении и обработке данных.
11. Перед отправкой данных стороннему LLM-провайдеру должна быть согласована политика обработки и регион хранения данных.
12. Должен существовать процесс удаления данных пользователя в соответствии с применимыми требованиями законодательства и политиками компании.

### 14.1. Аутентификация, права и аудит

| Роль | Обязательная аутентификация | Минимальные разрешения |
|---|---|---|
| Гость | Сессионный идентификатор и защита от подмены сессии | Чтение публичных данных; изменение только своей гостевой корзины |
| Авторизованный клиент | Механизм текущего сайта ekt.kz | Чтение публичных данных; изменение только собственной корзины и истории |
| Менеджер | Корпоративная аутентификация, MFA для production | Чтение только назначенных обращений и предоставленных по согласию контактов |
| Контент-менеджер | Корпоративная аутентификация, MFA для production | Создание и публикация базы знаний без доступа к секретам и корзинам |
| Администратор | Корпоративная аутентификация, MFA для production | Настройки и мониторинг по принципу минимальных привилегий; доступ к секретам выдаётся отдельно |

- RBAC применяется на сервере к каждому административному запросу; скрытие элемента интерфейса не считается контролем доступа.
- Выдача и отзыв привилегий журналируются, согласуются владельцем системы и пересматриваются не реже одного раза в квартал.
- Аудит-лог фиксирует вход, изменение настроек, публикацию базы знаний, доступ к обращениям и управление правами; пользователь не может изменить собственные записи аудита.
- Сроки хранения диалогов, вложений, журналов и срок исполнения запроса на удаление утверждаются до production-запуска и реализуются как автоматические политики. До утверждения этой политики обработка реальных персональных данных в промышленном контуре запрещена.

## 15. Логирование, мониторинг и аналитика

### 15.1. Технические события

- идентификатор запроса/трассы;
- обезличенный идентификатор сессии;
- тип намерения и вызванный инструмент;

- доля пустых результатов;
- ошибки API по типам;

- предотвращённые повторы операций;
- доля эскалаций;

### 15.3. Оповещения

Критические оповещения: серия `401/403`, массовые ошибки detail API, невозможность изменить корзину, просроченная синхронизация каталога, рост ошибок LLM и подозрение на утечку секрета.

### 16.3. Условия приёмки MVP

MVP принимается, если:

1. Все требования P0 реализованы либо имеют письменное согласованное исключение. Не допускаются исключения из запрета ложных цены/наличия, запрета изменения корзины без действительного подтверждения, изоляции секретов и проверки принадлежности корзины.
2. Все обязательные приёмочные сценарии P0 пройдены.
3. Нет дефектов уровня Critical/Blocker и открытых уязвимостей с CVSS 7.0 и выше либо эквивалентным уровнем по утверждённой корпоративной шкале. Шкала дефектов и ответственные за triage утверждаются до приёмки.
4. Ни один тест не фиксирует ложную цену, ложное наличие или изменение корзины без подтверждения.
5. Репозиторий, инструкции запуска, конфигурация окружений и демонстрационный сценарий переданы заказчику.

## 18. Этапы выполнения

1. **Немедленный запрос доступа:** в первый рабочий час отправить организаторам единый запрос на credentials, whitelist, примеры ответов, лимиты и контакт технического владельца; назначить ответственного и срок эскалации.
2. **Параллельный data fallback:** не дожидаясь ответа, реализовать fixture provider и синтетический каталог по разделу 8.7.
3. **Уточнение контрактов:** проверить реальный API, пагинацию и `offers`, правила складов, API корзины, базу знаний и сертификаты.
4. **Прототип данных:** загрузка каталога, нормализация, индекс и одинаковые контрактные тесты для fixture/live provider.
5. **MVP диалога:** поиск, карточка товара, цена/наличие, обработка ошибок.
6. **Аналоги и база знаний:** категорийные правила, сравнительная карточка, статичные условия покупки и обработка конфликтов источников.
7. **Корзина:** подтверждение, повторная проверка, идемпотентность и ссылка.
8. **Winning feature:** казахская локализация сквозного сценария с редакторской проверкой.
9. **Качество и репетиция:** безопасность, доступность, наблюдаемость, приёмочные тесты и два прогона демо — с live API и с принудительным fixture fallback.
10. **Пилот:** ограниченный трафик, сбор метрик, анализ ошибок и корректировка правил.

## 20. Риски и меры снижения

| Риск | Последствие | Мера |
|---|---|---|
| API-доступ не выдан или выдан в последний момент | Команда не успевает закрыть поиск и наличие | Немедленный запрос доступа, fixture provider с тем же контрактом, переключатель источника и общие contract tests |
| Неполная/меняющаяся схема API | Ошибки интеграции | Контрактные тесты, tolerant reader, версионирование адаптера |
| Неясная семантика складов | Ложное наличие | Allowlist и версионируемое правило доступности |
| Устаревший поисковый индекс | Неверный выбор | Detail-проверка перед ответом и корзиной |
| Галлюцинация модели | Недостоверная консультация | RAG, типизированные инструменты, отказ при отсутствии источника |
| Prompt injection из каталога/файла | Нарушение политик и утечка | Изоляция инструкций, валидация инструментов, минимальные права |
| Повтор операции после сетевой ошибки | Дубликат в корзине | Idempotency key и чтение фактического состояния |
| Отсутствие структурированных категорий | Слабые аналоги | Категорийная нормализация и ручная контрольная выборка |
| Официальные страницы условий противоречат друг другу | Недостоверный ответ на must-have вопрос | Версионируемая статичная KB, статус `conflicted`, безопасный отказ и письменное решение владельца контента |
| Недоступность API или LLM | Невозможность ответа | Тайм-ауты, контролируемая деградация, мониторинг, эскалация |
| Утечка персональных данных | Юридический и репутационный ущерб | Минимизация данных, маскирование, сроки хранения, контроль доступа |

## 22. Definition of Done

Работа считается завершённой, когда код размещён в репозитории, решение развёртывается по документации в чистом окружении, секреты вынесены из кода, P0-требования и приёмочные сценарии выполнены, критические события наблюдаемы, а владелец продукта подтвердил демонстрацию следующих сквозных сценариев:

1. поиск и консультация по существующему товару;
2. отсутствие товара и объяснимый подбор аналога;
3. ответ по условиям покупки из утверждённого источника;
4. отсутствие изменения корзины без подтверждения;
5. повторная проверка и успешное добавление после подтверждения;
6. безопасное поведение при недоступности API или недостатке данных;
7. переключение на явно маркированный `DEMO FIXTURE` без изменения бизнес-логики;
8. корректные ответы по статичной базе знаний, включая отказ выбирать конфликтующий порог доставки;
9. сквозной сценарий на казахском языке для статуса P1/WIN.
